How to use this guide

This handbook is the teaching companion to the Student Programme Guide, the Complete Course slide deck, and the Presenters Guide. Use it session-by-session from introduction through practicals and CV coaching.

Companion materials

  • Student Programme Guide — share with learners (journey, tools, outcomes).
  • Course Preview — learner-facing slides.
  • Presenters Guide — same slides with bottom presenter notes (theory spine, slides 1–144).
  • This Instructor Guide — pacing, lab runbooks, ISTQB Fridays, CV coaching, sign-off.

How each phase page is organised

  • Intent — what learners must leave knowing or able to do.
  • Source slides / notes — where to teach from.
  • Session flow — teach → demo → practice → check.
  • Talking points — compressed summary from the course manual & notes.
  • Lab / homework — practical evidence to collect.
  • Pitfalls — common learner blockers.
Delivery model: 12–16 weeks · ~2 hrs daily self-study · Sat–Sun live (2–4 hrs) · Friday ISTQB classes · online tutor support. Theory from the slide deck first; practicals (Postman, Azure DevOps, Visual Studio frameworks) once STLC and techniques are secure.

Phase 1A — Systems foundations

Slides 7–181–2 live blocksComputer, binary, hardware/software, networks

Intent

Give non-technical learners a shared vocabulary: computers, binary, software types, client–server communication. This underpins later API and environment talks.

Checks for understanding

  • Name hardware vs software with one everyday example each.
  • Explain (simply) how a phone reaches a server.
  • Why testers care about networks/APIs (failure location).

Summary notes for teaching

  • Binary is how machines represent data — testers meet it as encodings, flags, and “odd” stored values.
  • Software types (system vs application) frame what we test.
  • Client → network → server is the mental model for UI vs API failures (presenter note on Slide 17).
  • Use the network-devices diagram (Slide 18) as a slow walkthrough, not a rush.
ISTQB hook: Plant the idea that defects can sit in interface, logic, or data — revisited on objectives / layers slides.

Phase 1B — Waterfall & requirements

Slides 19–441–2 live blocksBRD / FRS, design, build, test, deploy, maintain

Session flow

  1. Methodologies list — focus Waterfall, V-Model, Agile (Slide 20 note).
  2. Waterfall cascade — same stages exist in every method; order/overlap change.
  3. BRD vs FRS with login / e-commerce examples from presenter notes.
  4. Design → development → system test → deploy (Azure focus) → ops.
  5. Close on Waterfall advantages vs challenges → why Agile emerged.

Summary notes

  • BRD = business view; FRS = testable detail (fields, rules, messages).
  • Testing should start when documents exist — not only at “System Test” box (Slide 36 note).
  • Cite real failure cost (e.g. Knight Capital) for “why testing matters”.
  • Cloud for this course = Microsoft Azure.

Homework

Learners write 5 BRD-level bullets and 5 FRS-level bullets for a “Forgot password” feature.

Phase 1C — Agile & Scrum

Slides 45–621–2 live blocksRoles, backlog, sprint ceremonies

Intent

Learners can describe Epic → Story → Task, name ceremonies, and explain continuous testing inside the sprint.

Talking points

  • Agile keeps docs practical; delivery + feedback over late big-bang releases.

Page 9

Phase 1D — V-Model

Slides 63–72~1 live blockVerification & validation pairing

Summary notes

  • Each left-side development stage pairs with a right-side test level.
  • Requirements ↔ Acceptance; System design ↔ System test; Architecture ↔ Integration; Module design ↔ Unit.
  • Coding sits at the bottom; execution climbs the right side.
  • Strength: early test design. Challenge: change cost if requirements shift late.

Teach tip

Draw the V live once. Ask: “If the FRS is wrong, which test level fails first in production impact?” Guide them to acceptance / system, then show how earlier reviews prevent that.

ISTQB: V-Model questions often test pairing of levels — drill the pairs every Friday until automatic.

Phase 1F — STLC (plan → close)

Slides 82–1122–3 live blocksCore manual-testing professional practice

Session flow (recommended split)

  1. Block A: Six STLC phases diagram → Requirement analysis → Test planning (plan contents, RACI, scope, approach, entry/exit, suspension, deliverables, schedule, risks).
  2. Block B: Scenarios → Cases → Scripts → Expected results → RTM.
  3. Block C: Environments (Dev→Live) → Execution Pass/Fail → Bug workflow → Retest / UAT defects → Closure.

Summary notes

  • One scenario → many cases; cases need data + expected results.
  • RTM proves coverage: requirement ↔ cases.
  • Bug loop: log → triage → fix → retest → closed (same in Jira or Azure DevOps).
  • Evidence beats opinion: steps, data, screenshots, environment.

Bridge to Phase 2

Promise: “Next we will do this end-to-end in Azure DevOps — User Story → Test Case → Bug → Retest.” Keep vocabulary identical so the tool feels like paperwork they already understand.

Phase 1H — Non-functional & maintenance

Slides 134–144~1 live blockQuality attributes + regression vocabulary

Summary notes

Phase 2 — Manual UI testing with Azure DevOps

Practical lab2–3 live weekendsUser Story → Test Case → Bug → Retest

Lab objective

Every learner executes a small UI feature end-to-end in Azure DevOps and produces portfolio evidence (exported cases, bug with attachments, retest result).

Instructor demo (30–40 min)

  1. Open ADO project board / Backlog.
  2. Create/refine a User Story with acceptance criteria.
  3. Create Test Plan / Suite / Cases linked to the story.
  4. Run a test → Fail → create Bug with steps, expected vs actual, severity, evidence.
  5. Simulate fix → Retest → mark Passed / close bug.

Learner practice

  • App under test: agreed training site (or instructor-hosted demo app).
  • Minimum: 1 story, 8–12 cases (positive + negative + BVA where relevant), 1 bug, 1 retest.
  • Capture screenshots in ticket and in personal portfolio folder.

Sign-off criteria

  • Cases are requirement-backed and atomic.
  • Bug is reproducible by a peer without asking questions.
  • Learner can narrate the workflow without reading notes.
Teaching link: Reuse STLC language from slides 96–110 so ADO feels familiar. Mention Jira parity (fields differ; process does not).

Phase 3 — Manual API testing with Postman

Practical lab2 live weekendsPostman + Swagger / OpenAPI

Session flow

  1. Recap client–server & JSON from foundations.
  2. Open Swagger/OpenAPI docs — identify resources, verbs, schemas.
  3. Postman: collections, environments, variables, auth (API key / Bearer).
  4. Send GET/POST/PUT/PATCH/DELETE; read status codes & body.
  5. Write test scripts (status, JSON property asserts) — still “manual API” mindset with light scripting.
  6. Negative tests: bad auth, missing fields, wrong IDs.

Portfolio evidence

  • Exported Postman Collection + Environment.
  • Short README: base URL, auth setup, 10+ requests covering CRUD + negatives.
  • 2–3 screenshots of failing vs passing assertions.

Pitfalls

  • Learners paste tokens into screenshots — teach redaction.
  • Treating 200 as always success — assert body too.
  • Skipping Swagger and guessing URLs.

Phase 6A — UI automation framework (Visual Studio)

Practical lab2–3 weekendsSelenium · Reqnroll/BDD · NuGet

Framework shape to teach

Solution folders: Tests (NUnit/xUnit or Reqnroll features) · Pages (Page Object Model) · Core (Driver factory, waits, config) · Utilities (reporting, screenshots). NuGet: Selenium.WebDriver, Selenium.Support, wait helpers, Reqnroll, assertions, reporting.

Live build sequence

  1. Create NUnit/xUnit test project in Visual Studio.
  2. Install NuGet packages; restore; tip: commit packages.lock / use PackageReference.
  3. Driver factory (Chrome) + quit in teardown.
  4. First raw test (login or search) — then refactor to Page Objects.
  5. Add Reqnroll feature file (Given/When/Then) binding to steps.
  6. Add screenshot on failure + simple HTML/Extent report.

Learner outcomes

  • Explain POM and why selectors live in pages.
  • Run tests from Test Explorer and command line (dotnet test).
  • At least 5 scenarios automated from earlier manual cases.

Pitfalls

  • Brittle absolute XPaths — teach relative + waits.
  • No waits → flaky demos live.
  • Secrets in repo — use user secrets / env vars.

Appendix A — ISTQB summary notes (1/2)

Condensed teach-from notes drawn from the course manual, presenter notes, and CTFL-aligned vocabulary. Use on Fridays and as revision handouts.

Fundamentals

  • Testing shows presence of defects, not their absence.
  • Exhaustive testing is impossible — use risk, priorities, techniques.
  • Early testing saves cost; defects cluster; pesticide paradox → refresh tests.
  • Testing is context-dependent; absence-of-errors fallacy (right product still matters).
  • Object of testing: compare behaviour to requirements; produce evidence.

Test levels (V-pairs)

  • Unit ↔ module design
  • Integration ↔ architecture
  • System ↔ system design
  • Acceptance ↔ requirements

Static testing / reviews

  • Walkthrough: author/BA/PO presents; many roles ask questions.
  • Peer review: testers review testware.
  • Technical review: architects/senior devs lead design critique.
  • Informal: quick two-person draft skim, light process.

Black-box techniques

  • EP: classes of inputs with same expected behaviour; pick representatives.
  • BVA: on and just beyond boundaries (inclusive/exclusive per spec).
  • State transition: valid sequences vs illegal shortcuts.
  • Decision / cause–effect: combinations of conditions → outcomes.
  • Experience-based: error guessing + exploratory (chartered).

Appendix A — ISTQB summary notes (2/2)

Types & vocabulary traps

  • Smoke (functional): build sanity — “does it start?”
  • Retesting: same failing case after a fix.
  • Regression: wider set for side effects of a change.
  • Non-functional: security, reliability, usability, performance (load/stress/spike/soak), availability, recovery.
  • White-box: structure visible (mostly developer unit/CI). Black-box: behaviour from outside (manual or automated).

Management snippets

  • Entry/exit criteria gate phases.
  • Risk-based testing directs depth.
  • Defect report: title, steps, expected vs actual, environment, evidence, severity/priority.
  • Traceability (RTM): requirements ↔ cases ↔ defects.

Friday drill set (rotate)

  • 10 MCQs timed (12–15 minutes).
  • One worked BVA/EP age or PIN example on whiteboard.
  • Two “who participates?” review questions.
  • One retest vs regression scenario story.
  • Learners write one wrong-answer explanation in their own words.
Pass strategy: vocabulary first, then techniques maths (BVA/EP), then process/management. Weak English readers: practise slow reading of stems — many errors are misread qualifiers (always / only / most).

Appendix B — Practical summary notes

Azure DevOps (UI)

  • Story with clear acceptance criteria.
  • Test Plan → Suite → Cases linked to story.
  • Run → Pass/Fail with comment + attachment.
  • Bug from failed run; severity; repro steps.
  • Retest after fix; close when evidence shows pass.

Postman (API)

  • Start from Swagger paths & schemas.
  • Environments for baseUrl + tokens.
  • CRUD + auth + negatives.
  • Assert status and body fields.
  • Export collection for portfolio.

VS automation

  • UI: Selenium + POM + waits + Reqnroll + reporter.
  • API: RestSharp client wrapper + DTOs + FluentAssertions.
  • NuGet PackageReference; run via Test Explorer / dotnet test.
  • CI: restore → test → publish results.
  • CV line = stack + count of scenarios + repo link.

Evidence standard (all practicals)

If a peer cannot reproduce the learner’s result from the artefact alone (repo README, ADO links/screenshots, Postman export), it is not yet portfolio-ready. Coach specificity over screenshots of green ticks with no context.
